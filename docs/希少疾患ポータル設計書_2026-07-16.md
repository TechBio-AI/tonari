- **位置づけ**: 本書は Phase0-T4/T5/T6(器の確立・公開ポータル区画・公開カラム)の続きとして、器を中核に据えた希少疾患ポータルの全体設計を定める。

- **決定事項(2026-07-16 創業者)**: ①主対象=**両面(顔を分ける)** ②患者フォロー=**Phase1では作らない** ③本書=**新規設計書として書き起こす**。

## 0. 一行の狙い

**「症状・疾患名から入り、出典付きの疾患情報を読み、対応できる専門医療機関の情報に辿り着く」までを、器の上に一本の動線として作る。個人の状態は判定しない。**

---

## 1. 設計原則(最上位・すべての判断をここに帰着させる)

CLAUDE.md / SCHEMA_CANON の再掲。ポータルのあらゆる機能はこの原則で可否を決める。

1. **公開面は器以外を読まない。** 公開されるのは器(themes / theme_facts / fact_sources)を通過し **approved かつ published** のものだけ。出典なき情報は存在させない。
2. **個人の状態には触れない。疾患一般を、出典と共に語る。** 「あなたは〜の可能性」「適合度%」「〜を受診してください」等の判定・助言・特定誘導は作らない・書かない・生成させない。
3. **要配慮個人情報を収集するフォーム・入力欄を作らない。** 症状入力は「情報検索クエリ」であって問診ではない(§4)。
4. **ガードレールは開発元専管。** ユーザーが該当性・広告表現ルールを緩められる機能は作らない。
5. **財務・課金・決済は一切作らない**(創業者専管)。

> 今日(2026-07-16)の実機検証で、旧 `/diagnosis` が確信度%・治療薬名・受診勧奨を個別化出力していることを確認した。これは原則2に反する**レガシー**であり(SCHEMA_CANON §2 で隔離済みと宣言)、ポータルの公開経路には**乗せない**。詳細は `docs/機能テストレポート_2026-07-16.md`。

## 2. アーキテクチャ:器を中心とした三層

```
        ┌─────────────────────────────────────────────┐
 [入口] │ 情報検索 / ナビゲーション(脱・診断)         │
        │  症状語・疾患名・遺伝子・診療科 → 関連疾患群   │
        └───────────────────┬─────────────────────────┘
                            ▼
        ┌─────────────────────────────────────────────┐
 [中核] │ 器 = themes / theme_facts / fact_sources      │
        │  疾患ページ(8ブロック)・すべて出典付き・承認済 │
        └───────────────────┬─────────────────────────┘
                            ▼
        ┌─────────────────────────────────────────────┐
 [出口] │ 専門医療機関・診療科の「情報提示」(ディレクトリ)│
        │  ※患者フォローは Phase1 では作らない(§7)      │
        └─────────────────────────────────────────────┘
```

### 2-1. 中核:器(既存・本番適用済み)

| テーブル | 役割 | ポータルでの使い方 |
|---|---|---|
| `themes` | 疾患の基本情報・国際コード・`slug`・`published_at`・承認状態 | 疾患ページ 1件 = theme 1件。URL は `/diseases/[slug]` |
| `theme_facts` | 情報の一片(種類ラベル `kind` + 中身 + 順序 + 承認状態) | 8ブロックの各項目を `kind` で表現(§3) |
| `fact_sources` | 出典(fact 単位で複数紐付け) | 各 fact に PMID/DOI/URL/ガイドライン等を必須で紐付け |

- 品質保証は**DBトリガで強制**(出典ゼロは承認不可・承認は reviewer のみ)。RLS 有効。この安全装置には触れない。
- 現状は**空の器**。中身の投入は §6 の供給ラインで行う。

### 2-2. 8ブロック → theme_facts の kind マッピング

survey の8ブロックを、器の汎用 `theme_facts.kind` として表現する(スキーマを増やさず器の柔軟性で吸収)。

| ブロック | kind(案) | 公開面での表示 |
|---|---|---|
| basic | `basic` | 疾患概要・別名・国際コード |
| diagnostic_delay | `diagnostic_delay` | 診断までの遅延(独自価値) |
| clinical_features | `clinical_feature` | 臨床的特徴(症状の一般情報) |
| differential | `differential` | 鑑別に挙がる疾患(情報として) |
| diagnosis | `diagnosis_method` | 検査・確定に用いられる方法(一般情報) |
| treatment | `treatment` | 治療選択肢(一般情報・個別処方はしない) |
| specialty_routing | `specialty` | 対応する診療科・専門領域 |
| diagnostic_flow | `diagnostic_flow` | 診断に至る一般的な流れ |

> `kind` の確定値・表示順・必須/任意は Phase1 実装前に別途 fix(過剰設計を避け、まず basic / clinical_feature / diagnosis_method / specialty から)。

### 2-3. 入口:症状検索を「診断」から「情報ナビ」へ

- 入力は**情報検索クエリ**(症状語・疾患名・遺伝子・診療科)。問診フォームではない。要配慮個人情報(既往・服薬・個人識別子)は**収集しない**。
- 出力は「その語に**関連情報が存在する**疾患ページへの導線」。**確信度%・順位付き診断候補・受診勧奨は出さない**。「これらの疾患に関連情報があります(出典付き)」という**情報提供**に留める。
- 表現例(可): 「入力に関連する疾患情報」。表現例(不可): 「あなたに最も可能性が高い疾患」「適合度80%」。

### 2-4. 出口:専門医療機関・診療科の情報提示

- **個別マッチング(「あなたはこの先生へ」)は特定誘導でNG**。疾患ページから「この疾患に対応する診療科・専門医療機関の**情報**」へ辿れる**ディレクトリ型**にする。
- データはやはり器(出典付き)経由。医療機関情報の一次ソース(学会の専門医リスト・指定医療機関等)を出典として持つ。
- **患者フォロー(受診後の追跡・PHI保持)は Phase1 では作らない**(§7・§8)。

## 3. 両面アクセスモデル(顔を分ける)

| 面 | 対象 | 認証 | 読むデータ | できること |
|---|---|---|---|---|
| **公開面** `app/(portal)/` | 患者・家族・医療従事者・一般 | 不要(将来Basic/公開) | 器の approved+published のみ | 疾患情報の検索・閲覧。個別化なし |
| **医療者面** | ログインした医療従事者 | 必要(Supabase Auth + role) | 器 + 医療者向け付加機能 | Phase2以降で定義(フォロー等はPhase3) |

- 公開面は**個人の状態に触れない**ことで、患者・家族も安全に使える。SEO資産にもなる。
- 医療者面の具体機能は Phase2 で設計。**フォロー/PHIはPhase3・弁護士レビュー前提**(本書では器の外・保留)。

## 4. データ供給ライン(最重要・ここが実質のプロダクト)

空の器に**出典付きで**中身を入れる工程。ここが品質と規制適合の生命線。

1. **一次情報の収集**: Orphanet(ライセンス確認要)・指定難病情報・査読論文・診療ガイドライン等。ライセンス不明データは使用前に創業者判断(CLAUDE.md)。
2. **fact 化 + 出典紐付け**: 各情報の一片を `theme_facts` に、対応する出典を `fact_sources` に。**出典なき fact は承認不可**(トリガが強制)。
3. **承認**: reviewer による品質判定(将来は薬事・弁護士レビュー対象を `docs/弁護士レビュー対象一覧.md` に沿って)。
4. **公開**: `published_at` を立てる(承認と公開は別軸)。

> **旧JSONコーパス(1001件)・旧RAG・レガシーテーブルは「下書きの材料」としてのみ使用可。出典を持たないため、そのまま公開経路には乗せない**(SCHEMA_CANON §3)。今日の検証で旧知識JSONに出典フィールドが無いことを確認済み。

## 5. 検索層の設計(入口を支える)

今日の検証で、旧エンジンは**ほぼ完全一致の文字列照合**で、臨床用語(例「手足の灼熱痛」)が格納語(「手足の痛み」)と綴り違いだと目的疾患を引けないことが判明した。ポータルの入口はこれを作り替える。

- **段階1(Phase1)**: 器の fact(症状の一般情報)に対する**同義語・用語正規化**を持つ検索。最低限、表記揺れ・臨床語⇄口語を吸収する辞書。
- **段階2(Phase2+)**: ベクトル検索(現状 Chroma は空=0件)。器の承認済み fact のみを埋め込み対象にする。
- confidence%・順位付けは**出さない**(原則2)。検索は「関連情報の有無」を返すだけ。

## 7. 明示的な非ゴール(Phase1 で作らないもの)

- 診断・症状チェッカー・リスク/重症度スコア・確信度%・個別化助言・受診勧奨(恒久的に非ゴール)。
- 要配慮個人情報を収集するフォーム(既往・服薬・個人識別子の入力欄)。
- 患者フォロー・PHI保持(Phase3・弁護士レビュー前提)。
- 課金・決済・財務(創業者専管・恒久非ゴール)。
- ユーザーがガードレールを編集/緩和できる機能。

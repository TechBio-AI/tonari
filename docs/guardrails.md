## 1. 「診断」を患者向けサービスの動詞として使わない

- 患者・一般利用者が目にする文言では「診断する」「診断結果」「diagnose」を使わない。
  「情報検索」「情報提供」「候補の提示」「鑑別の参考情報」に統一する。
- 判定・助言・特定誘導（「あなたは〜の可能性」「適合度」「〜を受診してください」）は作らない・書かない・生成させない。
- **対象外**: 内部の API 名・関数名・ファイル名（`/api/diagnosis`、`DiagnosisEngine` など）。
  改名はコストに見合わないので、名前は残し、画面文言だけを規範に合わせる。
- 出典: `CLAUDE.md` Critical Rules #1、公開面の最上位規範 2。禁止語リストは `docs/wording-blocklist.txt`。

## 2. パーセンテージを単独で表示しない。必ず実数の内訳を併記する

- 「一致度 50%」のような数字だけの表示は禁止。「登録症状 20 件中 1 件が一致」のように、分子と分母の実数を必ず添える。
- 理由: 現行フォールバックエンジンの `confidenceScore` は「表示候補の中での取り分」であり、
  確からしさではない（候補が1件なら必ず 100 になる）。数字だけ見せると確率と誤読される。
  経緯は `docs/survey_search_regression.md`、修正は commit `dacaf9c`。
- プロトタイプの流儀（`_reference/raredx-prototype/lib/search.php`）も同じ。
  「登録症状の数は分母に使わない。件数は実数の内訳として表示するだけ」。取り込む際もこの原則を崩さない。

## 3. HPO 原本は無改変・バージョン明示・コンソーシアムの引用

- `data/hpo/` の原本（`hp.obo` / `phenotype.hpoa` / `hp-ja.babelon.tsv`）は 1 バイトも変更しない。
  読み取り専用（`-r--r--r--`）を維持し、SHA-256 が `data/hpo/SOURCE.md` の記載と一致し続けること。
- 使用バージョンは **v2026-06-23**。DB や画面に HPO 由来データを出すときは必ず参照バージョンを明示する。
  日本語訳は `2023-07-21` 時点の翻訳であり本体より約3年古い。この差も隠さない。
- 加工・派生データは `data/hpo/` の外に出力し、派生物であることを明示する。
  独自の症状を HPO ID に紐付けて「HPO のデータ」として配布しない。
- 公開面には HPO コンソーシアムの帰属表示を掲出する（文面は `SOURCE.md` 条件3）。
- 出典: `data/hpo/SOURCE.md`（ライセンス3条件）、`docs/survey_hpo_acquisition.md`。

## 4. symptom_patterns 1,880 語は捨てない

- `data/knowledge/comprehensive_rare_diseases_knowledge.json` の `symptom_patterns`（重複排除で 1,880 語）は、
  HPO に無い唯一の**口語**資産である（HPO の日本語同義語ファイルは空）。
- 知識ベースを作り直す・DB へ移す・HPO へ写像する、いずれの場合も 1,880 語を減らさない。
  写像できなかった語も削除せず「未写像」として保持する。
- 減ったかどうかは `docs/asset_snapshot_2026-08-29.json` の `symptom_patterns_unique` と比較して検知する。
- 同 JSON の `symptoms`（1,962 語）との和集合 3,663 語も同様に減らさない。疾患の**概念**も減らさない。
  同一疾患が複数レコードに割れているものの統合はこれに含めない（統合時は消える側の語・別名・検査・治療をすべて残す側に合算する。
  基準線: 2026-09-13 統合後 951 件、`docs/kb_restructure_apply_log_2026-09-13.md`）。
- 出典: `docs/survey_hpo_acquisition.md` 方針 B（「これが本命」）。

## 5. 検索データは保存しない方向へ寄せる。症例データは匿名化エンジンを通す

- 症状検索（AI症状検索）の入力・結果は、原則としてサーバ側に永続化しない方向へ設計を寄せる。
  現行の `diagnosis_history` 保存は既存挙動として残っているが、これを拡張しない。
- 症例（フォローアップ・転帰など個人に結び付きうるデータ）を集計・開示・外部提供する経路は、
  必ず `lib/services/anonymization-engine.ts` を通す。直接クエリで生データを外に出さない。
- 個人識別子を含むペイロードを外部 LLM API へ送らない（`CLAUDE.md` Critical Rules #3。技術的に多重防御する）。
- 匿名化エンジンは製薬系ディレクトリの外（`lib/services/`）に置き、製薬系を切っても巻き込まれない状態を保つ。
  現状は独立している（`docs/survey_pharma_dependencies_2026-08-29.md` (3)）。
- 2026-09-26: 製薬系は別リポジトリ `hozon-pharma-followup` へ切り出す（`docs/DECISIONS.md`）。切り出し後、メインでは
  匿名化エンジンの呼び出し元が 0 になるが、**使われていないという理由で消さない**（将来の患者コミュニティで使う資産）。

## 6. 財務・認証情報に AI は触れない

- 契約・アップグレード・API キー発行・カード情報・予算閾値（`infra/budget/budget.conf` の `DAILY_LIMIT_USD` 等）は
  AI 艦隊が読まない・書かない・変えない。提案のみ可。
- `.env*`、`credentials.json`、鍵ファイル、OS キーチェーンにアクセスしない。
- 自動停止メカニズム（予算ウォッチドッグ）を解除・無効化しない。
- 出典: `CLAUDE.md` ABSOLUTE PROHIBITIONS 1〜5、Critical Rule #4、#9。

- `/Users/techbio/Projects/_reference/raredx-prototype` は読むだけ。1 文字も変更しない。

## 運用ルール

- 新機能を作る前に、`node_modules/.bin/jest` を実行し、失敗一覧が基準線（スナップショットの `test_baseline`）から増えていないことを確認する。
- 特性評価テストが赤くなったら、「意図した変更か」を先に問う。意図した変更なら期待値を更新し、理由をコミットメッセージに書く。
- 受け入れテストが緑になったら、`acceptance/cases.yaml` にベクターを追加して次の目標を置く。緑を減らす変更は退行。

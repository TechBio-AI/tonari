# 知識ベース側の課題（フェーズ0 で発見、フェーズ0 では直さない）

- 発見日: 2026-09-05（ファイル名の日付はタスク指示書上の 2026-08-29）
- 対象: `data/knowledge/comprehensive_rare_diseases_knowledge.json`（1,001 疾患、症状語 3,663）
- 位置づけ: 受け入れテスト（`acceptance/cases.yaml`）の前提確認で見つかった、**照合で回避すべきではなく知識ベース側で解くべき問題**。
  フェーズ0 では記録のみ。テストは `kb_aliases` で名前差を吸収しているが、それは暫定であり、ここに書いた問題が解けたら `kb_aliases` は不要になる。

## 1. 「家族性地中海熱」が独立した疾患として収録されていない

- 現状: 疾患名 `自己炎症性疾患`（`orpha_code: ORPHA:342`）の `alternate_names` に
  `["家族性地中海熱", "FMF", "Familial Mediterranean Fever"]` として入っている。
- 問題: ORPHA:342 は家族性地中海熱そのものの Orphanet コードであり、「自己炎症性疾患」は上位概念（疾患群）の名前。
  レコードの主名と ORPHA コードが指す粒度が食い違っている。
  症状も FMF のもの（`周期的発熱 / 腹膜炎 / 胸膜炎 / 関節炎 / アミロイドーシス`）で、疾患群としての記述ではない。
- 影響: 検索結果に「自己炎症性疾患」と表示され、患者・医師が探している「家族性地中海熱」の名前が出ない。
  受け入れテスト `fmf-colloquial` の `rank_1: 家族性地中海熱` は、名前だけでも一致しない。
- 対応の方向（フェーズ1 以降）: 家族性地中海熱を独立した疾患レコード（主名 = 家族性地中海熱、ORPHA:342）にする。
  「自己炎症性疾患」を残すなら疾患群レコードとして分け、ORPHA コードは付け直す。
- 判断が必要な点: 他の自己炎症性疾患（TRAPS、CAPS、HIDS 等）の収録状況を確認してから決める。
- **フェーズ1 での確認（2026-09-05、フェーズ2 以降で解く課題として明記）**:
  日本語正規化層（`lib/normalization/`）を前段に置いても `fmf-colloquial` は緑にならない。原因は知識ベース側にある。
  - 「自己炎症性疾患」（＝FMF）の登録語は `周期的発熱／周期的に高熱／お腹が痛い` で、「腹痛」「繰り返す発熱」を持たない。
  - 一方 TRAPS・高IgD症候群・Mevalonate Kinase欠損症・カロリ病は `周期的発熱／腹痛／お腹が痛い` を揃って持つ。
    「繰り返す発熱＋腹痛」の 2 概念で当てる限り、FMF がこれらに勝つ根拠が知識ベースに無い。
  - 実測（前段あり、フォールバックエンジン）: カロリ病 3 件 ＞ ANCA関連血管炎ほか 2 件。FMF は上位 5 件に入らない。
  - プロトタイプで FMF が 1 位だったのは、収録 6 疾患のうち「繰り返す発熱＋繰り返す腹痛」を持つのが FMF だけだったから。
    プロトタイプ式の重み（1÷登録疾患数）を持ち込んでも、上記 4〜5 疾患は同点になる。
  - 解く順序: (1) FMF を独立レコード（主名 = 家族性地中海熱、ORPHA:342）にし、症状語を整える
    （繰り返す発熱・反復性腹痛・胸痛・関節痛・漿膜炎・アミロイドーシス等。`symptom_patterns` は減らさない）。
    (2) 言い回しの数ではなく概念の数で数えるエンジンへ差し替える（課題 7）。
  - 受け入れテストの `kb_aliases`（名前の照合）は障害ではない。名前は既に吸収できている。

## 2. 「遺伝性ATTRアミロイドーシス」に表記ゆれが複数ある

現行知識には、同じ疾患を指すと思われるレコードが少なくとも 2 件ある。

| 主名 | alternate_names | orpha_code |
|---|---|---|
| `遺伝性ATTR型アミロイドーシス` | `hATTR`, `家族性アミロイドポリニューロパチー` | 要確認 |
| `遺伝性ニューロパチー伴うアミロイドーシス` | `ATTRv`, `遺伝性TTRアミロイドーシス`, `hereditary ATTR Amyloidosis` | 要確認 |

さらに関連レコードとして `遺伝性アミロイドニューロパチー（V30M以外）`（`ATTRv non-V30M`）、
`老人性全身性アミロイドーシス`（`ATTRwt`、これは遺伝性ではない）がある。

- 問題: 「遺伝性ATTRアミロイドーシス」（受け入れテストの期待名、臨床で一般的な呼び方）で完全一致するレコードが無い。
  同じ疾患が 2 レコードに割れているため、症状が両方に分散し、検索でどちらも上位に来にくい
  （実測: `["手足のしびれ", "手足に力が入らない"]` で `遺伝性ATTR型アミロイドーシス` が 4 位、もう一方は圏外）。
- 対応の方向: どちらが正か（あるいは統合すべきか）を、ORPHA コード（Orphanet の hATTR = ORPHA:85447）と
  指定難病の名称（「家族性アミロイドーシス」）を突き合わせて決める。統合するなら症状・別名を合算し、
  `symptom_patterns` は 1 語も落とさない（`docs/guardrails.md` 4）。
- 判断が必要な点: 「V30M 以外」を別レコードとして残す意味があるか。

## 3. 「汗をかきにくい」が症状語 3,663 語に無い（重要）

- 現状: 症状語（`symptoms` ∪ `symptom_patterns`）に「汗をかきにくい」は存在しない。
  ファブリー病のレコードには `無汗症` / `低汗症`（symptoms）、`汗が出ない` / `汗をかかない`（symptom_patterns）がある。
- 問題: ファブリー病の低汗症は診断の鍵になる所見だが、患者や医師が実際に使う言い方
  「汗をかきにくい」で引けない。現行エンジンは疾患側パターンが入力文の部分文字列であるときしか当たらないため、
  「汗をかかない」と「汗をかきにくい」は別物として扱われる。
- 実測（2026-09-05、フォールバックエンジン）: 入力 `["手足の痛み", "汗をかきにくい"]` →
  ファブリー病は「手足の痛み」1 語だけで一致し、Gorham-Stout病（「痛み」の部分一致）と同点 50 で並ぶ。
  「汗をかきにくい」は何にも寄与していない。
- **フェーズ1 で解決（2026-09-05）**: 別名辞書 `lib/normalization/alias-groups.ts` の概念 9（汗をかきにくい ← 汗が出ない／汗をかかない／汗が出にくい／低汗症／無汗症）に
  完全一致し、前段が現行語彙 5 語を展開する。実測: ファブリー病 5 件（45）、2 位 特発性後天性全身性無汗症 2 件（18）。`fabry-teen-male` は緑。
- 位置づけ: これは **フェーズ1（日本語正規化層）で解くべき問題の具体例**である。
  「汗が出ない」「汗をかかない」「無汗症」「低汗症」「汗をかきにくい」を同じ概念（HPO: HP:0000966 Hypohidrosis 相当）に束ねる層が要る。
  語彙を 1 語追加して済ませるのではなく、言い換え（〜しにくい / 〜が出ない / 〜しない）を吸収する仕組みで解く。
- 受け入れテストの扱い: `fabry-teen-male` は `precondition_missing` にせず red のまま残す。
  フェーズ1 でこれが緑になることが、正規化層が効いた証明になる。

## 4. 経路の実態（知識ベースではなくエンジン側だが、同じ文脈で記録）

- `app/api/diagnosis/route.ts:151-184`: 自由記載入力は `custom_` ID になるため、フォールバックエンジンが先に走る。
  フォールバックは候補 0 件のとき汎用候補 3 件を注入するため、**本命（HPO）エンジンには実質到達しない**。
- 本命エンジン（`lib/services/diagnosis-engine.ts:28-30`）は `custom_` / `parsed_` / `norm_` ID を照合対象から除外する。
  結果、自由記載だけを渡すと「詳細な評価が必要」1 件（confidence 0）か、候補 0 件になる。
  これが「本命エンジンが候補 0 件になる」原因の一つ。
- 現在の出力は `tests/characterization/diagnosis-engines.characterization.test.ts` で凍結済み。

## 5. 副次的に見つかった挙動（記録のみ）

- `symptoms` と `symptom_patterns` の両方に同じ語があると二重にカウントされる（「発熱」→ 一致 2 件と表示）。
  `registeredSymptomCount` も二重に数えている。実数の内訳表示（guardrails 2）の分母・分子が実態より大きい。
- 短いパターン（「痛み」「しびれ」）が長い入力の部分一致で無関係な疾患を拾う（Gorham-Stout病、副甲状腺機能低下症）。
  プロトタイプはこれを避けるため「無関係な候補を出すのは、何も出さないより悪い」として閾値を置いている
  （`_reference/raredx-prototype/lib/search.php` の `SIMILARITY_THRESHOLD`）。

## 7. 現行エンジンは「言い回しの数」を数えるため、正規化層で件数が水増しされる（フェーズ1 で顕在化、エンジン差し替え時に扱う）

- 発見日: 2026-09-05（フェーズ1 タスク5）
- 現象: フォールバックエンジンは、疾患側の `symptoms`＋`symptom_patterns` それぞれが入力文の部分文字列なら 1 件と数える。
  正規化層が 1 概念を複数の言い回し（例: 手足のしびれ／手足がしびれる／四肢のしびれ／末梢神経障害）へ展開すると、
  同じ概念の言い回しを多く持つ疾患ほど件数が増える。課題 5 の二重カウントと同根。
- 実測（`neuropathy-adult`、入力 `["手足のしびれ", "手足に力が入らない"]`）:
  前段なし = CIDP 2 件・副甲状腺機能低下症 2 件（同点） → 前段あり = **後縦靭帯骨化症 4 件**（手足がしびれる／四肢のしびれ／力が入らない／筋力低下）が単独 1 位、
  遺伝性ATTR型アミロイドーシス・CIDP ほかが 2 件。2 概念しか入れていないのに 4 件と数えている。
- CMT が上位に来ないのは、現行の CMT レコードがしびれ・脱力の口語を持たないため（知識ベース側。課題 2 と同じ文脈）。
- 方針（2026-09-05 ファウンダー決定）: フェーズ1 では記録に留める。単独では直さない。
  概念単位で数える（＝プロトタイプの `find_disease_candidates` の流儀）エンジンへ差し替えるときに、課題 5 と一緒に消える。
- 前段が返す `resolutions`（入力ごとの読み取り結果）には概念単位の情報があるので、差し替え時にそのまま使える。

## 8. 「先天性大脳白質形成不全症」（idx 588）の別名に別疾患「LBSL」が混入している（ORPHA 照合で発見）

- 発見日: 2026-09-10（`docs/orpha_correction_proposal_2026-08-29.md` §3.1）
- 現状: 主名 `先天性大脳白質形成不全症`、`alternate_names` = `["LBSL", "4H Leukodystrophy", "POLR3関連白質ジストロフィー"]`、`orpha_code` = `ORPHA:137898`（= LBSL）。
- 問題: 説明・症状・診断はすべて 4H 白質ジストロフィー（POLR3A/POLR3B 変異。低髄鞘化・歯牙低形成・低ゴナドトロピン性性腺機能低下の三徴）で、
  LBSL（DARS2 変異による脳幹・脊髄病変と高乳酸を伴う白質脳症）の要素は一つも無い。全く別の疾患の略号が別名に混入している。
- ORPHA 番号は 4H（ORPHA:289494）へ付け替えることをファウンダーが承認済み（2026-09-10、`docs/orpha_corrections_2026-08-29.json`）。
  **別名「LBSL」の除去は番号の作業とは別**で、ここに記録する。
- 対応の方向: 別名から `LBSL` を外す。LBSL を収録するなら独立レコード（主名 = LBSL または「脳幹・脊髄病変と高乳酸を伴う白質脳症」、ORPHA:137898）として作る。
  なお「先天性大脳白質形成不全症」は指定難病 131 の名称で、Pelizaeus-Merzbacher 病を含む群名でもある。主名の粒度もあわせて確認が要る。

## 9. 「良性家族性舞踏病」（idx 726）の記述が疾患名より広い概念（Brain-lung-thyroid syndrome）を書いている（ORPHA 照合で発見）

- 発見日: 2026-09-10（`docs/orpha_correction_proposal_2026-08-29.md` §3.1）
- 現状: 主名 `良性家族性舞踏病`、`alternate_names` = `["BHC", "NKX2-1関連疾患", "Brain-Lung-Thyroid Syndrome"]`、`orpha_code` = `ORPHA:1429`（= Benign hereditary chorea）。
  説明は「NKX2-1 遺伝子変異による脳・肺・甲状腺症候群」、症状に `甲状腺機能低下` `肺疾患（RDS/ILD）` を含む。
- 問題: 疾患名と ORPHA:1429 は正しく対応している。Brain-lung-thyroid syndrome（ORPHA:209905）は同じ NKX2-1 変異による、より広い表現型。
  記述だけが広い側を書いており、レコードの名前と記述の指す概念がずれている。
- 判断（2026-09-10 ファウンダー）: **番号は ORPHA:1429 を維持**（患者・医師はこの名前で探す。番号を広い側へ移すと名前と番号がずれる）。
  正しい対処は「番号を記述に合わせる」ではなく「記述を疾患名に合わせる」こと。番号ではなくレコード設計の問題。
- 対応の方向: 説明・症状を良性家族性舞踏病（小児期発症の非進行性舞踏運動、知的発達は概ね正常〜軽度遅れ）に絞る。
  Brain-lung-thyroid syndrome を収録するなら独立レコード（ORPHA:209905）として分け、別名からも外す。
  出典付きで作り直す際（`docs/SCHEMA_CANON.md`）に扱う。

## 11. 「中條-西村症候群」（idx 631）と「CANDLE症候群」（idx 623）が Orphanet では同一エンティティ（ORPHA 照合 v2 で発見）

## 22. 型番号を持つ疾患名が、名前順で人の感覚と違う順に並ぶ（ポータルの疾患一覧で発見。表示側の課題）

- 発見日: 2026-09-11
- 現象: 疾患一覧を名前順（`localeCompare(name, 'ja')`）で並べると、型番号の順序が崩れる。
  - ローマ数字: `ムコ多糖症III型 → II型 → IV型 → I型 → VI型`（I型が III型より後に来る）
  - 算用数字: `遺伝性痙性対麻痺11型 → 2型 → 3A型 → 4型 → 5A型 → 7型`（11型が 2型より先に来る）
- 原因: 文字列として比較しているため。
  - ローマ数字の場合、2 文字目以降でラテン文字（I・V）と漢字（型）を比べ、ラテン文字が先に来る。
    「II型」は 2 文字目が `I`、「I型」は 2 文字目が `型` なので、`II型` < `I型` になる。
  - 算用数字の場合、桁数を見ずに 1 文字ずつ比べるため `1` < `2` で「11型」が先に来る。
- 影響（実測。2026-09-11 時点の知識ファイル 1,001 件）:
  - ローマ数字の型を持つ病名 21 件。うち同じ疾患群が 2 件以上あって並びが目に見えて崩れるのは 6 群
    （ムコ多糖症 5 件、チロシン血症・グルタル酸血症・遺伝性感覚性ニューロパチー・骨形成不全症・糖原病 各 2 件）。
  - 算用数字の型を持つ病名 38 件。遺伝性痙性対麻痺（6 件）、脊髄小脳変性症などが該当。
  - なお `Intl.Collator` の `numeric: true` は算用数字だけを直す。ローマ数字には効かない（実測済み）。
- 対処案: ローマ数字を数値に変換して比較する。ただし次に注意すること。
  - 亜型の扱い。医学的にはムコ多糖症 III 型に A/B/C/D の亜型があるが、
    現在の知識ファイルには `IIIA型` の形は 1 件も無く、代わりに `糖原病Ia型`『遺伝性痙性対麻痺3A型』
    『5A型』のように算用数字＋英字の形で入っている。変換処理はこの形も壊さずに扱う必要がある。
  - 病名の途中に出るローマ数字と、型番号のローマ数字を取り違えないこと。
- 判断（2026-09-11 ファウンダー）: **保留**。実害が小さく（検索すれば同じ疾患群が並んで見えるので目的のものは見つかる。
  順番が不自然なだけ）、中途半端に直すと誤読のリスクがあるため。時間の都合ではない。
- 補足: 知識ベースを出典付きで作り直すとき（課題 21 の `reading` と同じ機会）に、
  並べ替え用の鍵（sort key）を持たせれば、表示側で推測せずに済む。

## 43. 認証の戻り先を request.url のオリジンで組み立てている（2026-09-21、/demo は修正済み・/auth は未修正）

- 内容: Route Handler で `new URL(request.url).origin` を戻り先に使うと、**踏んだホストと食い違うことがある**。
  開発サーバ（`next dev --hostname 0.0.0.0`）に `127.0.0.1:3000` で入っても、`request.url` のオリジンは
  `http://localhost:3000` になる。cookie はホスト単位なので、`127.0.0.1` に発行したセッション cookie は
  `localhost` へのリダイレクト先には送られない。
- 実害: `/demo` のマジックリンク認証が通らなかった。`exchangeCodeForSession` は成功して cookie も発行されたのに、
  戻り先が `localhost` だったため次のリクエストに cookie が一つも乗らず、middleware がセッション無しと判定して
  `/demo/login` へ送り返していた（2026-09-21 に確定・修正）。
- 修正済み: `app/demo/auth/callback/route.ts` と `app/demo/auth/signout/route.ts`。
  **戻り先を絶対 URL で組み立てるのをやめ、`Location` を相対パス（`/demo/community` 等）で返す**
  （`new NextResponse(null, { status: 303, headers: { Location } })`）。ブラウザが「いま見ているホスト」で
  解決するので、オリジンの食い違いが起きない。
  Host ヘッダから組み立てる案も検討したが、戻り先を外から差し替えられる形になるため採らなかった
  （2026-09-21 ファウンダー判定）。
- **未修正: `app/auth/callback/route.ts:5,36,40`。** 同じ書き方（`const { searchParams, origin } = new URL(request.url)` →
  テンプレート文字列で `origin + next` を組み立て）で、同じ食い違いが起きうる。
  こちらは医師・製薬会社向けの既存ログイン経路で、監査ログ書き込みも含むため、影響範囲を読んでから別途判断する。
  なお `app/**/route.ts` を全数確認した結果、戻り先に `origin` を使っているのはこの 1 件のみ。
- 本番（Vercel）では `x-forwarded-host` がプラットフォーム側で付くため、この食い違いは表に出にくい。
  **ローカル開発でだけ再現する種類の不具合**で、気付きにくい。

## 45. utils/supabase/middleware.ts の set が、応答を作り直して前の cookie を捨てる（2026-09-21、未修正）
